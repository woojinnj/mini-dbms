# 실측 벤치마크

측정 시각: 2026-11-16 10:18:03 KST. Python 3.13.2, macOS-26.6.2-arm64-arm-64bit-Mach-O.
원본: [100만 건 측정 JSON](../benchmarks/million-rows.json), [API 측정 JSON](../benchmarks/api-load.json).

## Phase 2 — 1,000,000행

| 항목 | 측정값 |
|---|---:|
| 총 행 수 | 1,000,000 |
| SQL INSERT 한 문장당 행 수 | 1,000 |
| INSERT 총 시간 | 7.985초 |
| INSERT 처리량 | 125,240행/초 |
| 테이블 파일 | 84,594,696 bytes (80.68 MiB) |
| 재시작 및 인덱스 재구성 | 2.619초 |
| ID 인덱스 조회 중앙값 | 0.057083ms |
| email 선형 탐색 중앙값 | 1509.066416ms |
| 중앙값 비율 | 26,436배 |
| ID 조회의 검사 행 수 | 1 |
| email 조회의 검사 행 수 | 1,000,000 |

100만 건 모두 `Database.execute(INSERT SQL)`을 통해 파서·검증·저장·B+ 트리 삽입을 거쳤습니다. 파일을 직접 생성해 적재를 우회하지 않았습니다. 1,000행 단위로 커밋하며 **fsync를 활성화**했습니다. 삽입 시간은 SQL 문자열 생성부터 파일 저장과 인덱스 갱신까지 포함합니다.

조회는 고정 seed 2026으로 선택한 5개 ID를 사용했습니다. 각 ID와 그에 대응하는 고유 email을 비교하며 두 SELECT의 전체 결과가 같은지 assert합니다. email에 UNIQUE 제약을 구현한 것은 아니므로 planner는 전체 파일을 스캔합니다. 양쪽 모두 LIMIT을 사용하지 않습니다.

측정 전 전체 COUNT로 OS 파일 캐시를 예열하고, 각 반복에서 인덱스/선형 조회 순서를 번갈아 실행했습니다. 조회 시간은 parser를 포함한 `Database.execute()` 전체의 wall clock입니다. 조회는 레코드 CRC32를 검증하며, 선형 탐색은 프레임 체크섬 검증도 포함합니다. 인덱스 측정은 DB가 이미 열린 상태로, 파일에서 인덱스를 만드는 시작 비용은 별도 항목으로 표시했습니다.

| 대상 ID | 인덱스 (ms) | 선형 탐색 (ms) |
|---|---:|---:|
| 124,907 | 0.057083 | 1509.066416 |
| 335,004 | 0.124458 | 1512.240000 |
| 526,926 | 0.054750 | 1507.429709 |
| 997,555 | 0.110750 | 1481.532209 |
| 536,686 | 0.052875 | 1524.433167 |

이 결과는 이 데이터·이 환경에서의 warm-cache 소규모 반복 측정입니다. 캐시가 차가운 상태, 넓은 결과 집합, 다른 저장 장치, 동시 부하, 데이터 분포에 대한 일반적인 성능 보장은 아닙니다. 26,000배 수준의 비율은 단일 레코드를 seek하는 작업과 100만 JSON 레코드를 읽고 비교하는 작업의 차이를 보여줍니다. 상용 DB와 비교한 수치도 아닙니다.

## Phase 3 — 실제 HTTP 서버 부하

| 항목 | 측정값 |
|---|---:|
| 동시 클라이언트 | 16 |
| 서버 worker | 8 |
| SQL 요청 수 | 1,000 (INSERT 500 + SELECT 500) |
| 총 소요 시간 | 0.175초 |
| 처리량 | 5,707요청/초 |
| 요청 latency 중앙값 | 2.623ms |
| 요청 latency p95 | 4.169ms |
| 최대 active worker | 8 |
| 오류 / 과부하 거절 | 0 / 0 |
| 정상 종료 후 파일 재오픈 검증 | 500행, 다음 ID 501 |

별도 프로세스로 `python -m minidb ... serve`를 실행하고 실제 loopback HTTP를 사용했습니다. 각 클라이언트는 INSERT로 받은 ID를 SELECT하여 해당 행이 정확한지 검사합니다. 모든 자동 ID가 중복 없이 연속인지, worker 수가 제한을 넘지 않는지, SIGTERM으로 정상 종료한 뒤 데이터가 남아 있는지도 확인합니다.

서버의 fsync는 활성화했습니다. 클라이언트 측 latency는 TCP 연결부터 응답 본문 수신까지 포함합니다. 각 요청은 새 연결을 사용합니다. 이 부하 테스트는 작은 데이터셋의 INSERT/ID 조회 혼합이며, 대규모 선형 탐색 부하 성능을 의미하지 않습니다. 요청 수가 작아 장시간 운영·tail latency의 대표값으로 해석해서는 안 됩니다.

## 재현 명령

```bash
python3 scripts/benchmark.py --rows 1000000 --output benchmarks/latest.json
python3 scripts/api_loadtest.py --pairs 500 --clients 16 --workers 8 --output benchmarks/api-load-latest.json
```

둘 다 임시 DB를 사용해 기존 DB를 수정하지 않습니다. 첫 번째 명령은 새 `--data-dir`을 지정하면 테이블 파일을 보관할 수 있습니다. JSON에 환경과 개별 조회 표본을 함께 기록하므로 다른 머신에서 비교할 수 있습니다.
